### 重要更正：关于「冗余索引」，我先前判断错了
先前的结论来自**临时库 create_all 的 DDL**，与生产库实际情况相反，切勿照搬：

- **生产库（手工建的表）没有冗余**，且 `username_UNIQUE` / `phone_UNIQUE` /
  `token_UNIQUE` 本身就是 `Non_unique=0` 的**唯一约束**。
  → 若执行 `DROP INDEX username_UNIQUE` 会**直接删掉唯一性约束**（事故）。
- 冗余只存在于 **create_all 新建的表**：列级 `unique=True` 生成 `UNIQUE KEY username`，
  `__table_args__` 里的 `Index("username_UNIQUE", ...)` 又生成一个**非唯一**同名 KEY。

教训：判断索引问题必须查生产库 `SHOW INDEX` 的 Non_unique 字段，
不能只看新建表的 DDL。

### 正确修法（已实施，生产库零 ALTER）
只改 ORM：`models/users.py` 中把 3 个 `Index(...)` 换成命名的
`UniqueConstraint("username", name="username_UNIQUE")` 等，并**去掉列级 unique=True**
（否则仍会多生成一个以列名命名的唯一索引）。
效果：新建表只剩一个唯一索引，且索引名与生产库完全一致。
验证：`user` 表新建 DDL 与生产库**逐行完全一致**；生产库数据 403/8/5/2 未变。

### 顺带发现的其他 ORM 与生产库差异（未修，非冗余问题）
1. `user_token` 外键：生产库 `ON DELETE CASCADE`，ORM 未声明 → 新环境删用户会残留 token。
2. `news_category` 唯一索引名：生产库 `name_UNIQUE`，ORM 生成 `name`（同类命名问题）。
3. `news.publish_time` 索引：生产库 `DESC`，ORM 默认 ASC。
4. 外键约束名不同（fk_user_token_user vs user_token_ibfk_1），仅命名差异。
